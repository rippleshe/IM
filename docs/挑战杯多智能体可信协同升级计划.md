## 0. 执行摘要

项目当前已经完成了主要工程骨架：PostgreSQL 单数据源、Redis/BullMQ 动态 DAG、SSE 事件流、12 题诊断、BKT、难度校准、混合检索、Claim 审核、反方质询、裁决、隐私门禁、六类资源、三类学习者、60 个评测案例和三个前端工作台。下一阶段不应推翻重做，也不应继续堆叠 Agent 名称。

下一阶段只围绕四条主线推进：

1. **可信协同协议**：每个 Agent 节点必须产出结构化、可引用、可散列、可回放的公开中间产物；上下游通过产物引用协作，不能只靠一段不可复核的聊天文案。
2. **幻觉治理闭环**：把草稿中的事实声明拆成 Claim，记录每轮证据、反证、质询、裁决和修订结果；生成端、批评端、裁决端保持上下文隔离；规则校验与 Agent 判断取更严格结果。
3. **个性化与事实保真同时验证**：同一任务在不同画像下，教学难度、脚手架、结构可以不同，但核心事实与证据边界必须一致；用反事实对照和消融实验证明“多 Agent 与学习者状态耦合”确实带来增益。
4. **轻量前端验证台与材料体系**：保留“路径—学习—资源”三个页面，在顶部新增一个“验证”页面；现有页面只补运行来源、决策理由、证据定位和反馈影响，不做大规模重构。

最终应形成一句清晰的技术主张：

> IM-Training-Agent 提出一套“学情图—声明证据图—协同运行链”耦合的可验证多智能体训练方法：学情图决定怎么教，声明证据图约束教什么，协同运行链记录为何这样决策；个性化可以变化，专业事实不可漂移。

## 1. 不可突破的开发约束

### 1.1 流量与依赖约束

在用户未再次明确授权前，开发 Agent 必须遵守：

- 不执行 `pnpm install`、`pnpm add`、`pnpm update`、`pnpm dlx`、`npx`。
- 不执行 `curl`、`wget`、`Invoke-WebRequest` 或任何下载脚本。
- 不执行 `pnpm data:metropt`、`pnpm docs:embed`，不重新拉取 MetroPT-3，不重新批量生成嵌入。
- 不执行会拉取镜像的 `docker pull`；运行 `docker compose build` 前必须确认所需镜像已在本机，且仍应优先避免构建。
- 不引入新的 npm 包，不修改 `pnpm-lock.yaml`。新能力使用现有 TypeScript、React、Next.js、Drizzle、Vitest、Node 标准库实现。
- 不下载外部字体、图片、图标、前端模板或数据集。前端继续使用现有 `lucide-react`、Tailwind 和已有组件。
- 默认不运行全量 live 评测。模型 API 调用同样会消耗网络流量；先用确定性单测、存量运行记录和离线回放验证。需要 live 生成时，先向用户说明预计案例数与调用量并取得授权。
- 所有常规验证优先使用 `pnpm test`、`pnpm typecheck` 和已有本地服务；若命令表现出自动安装倾向，立即停止。

### 1.2 工程约束

- 包管理只使用 pnpm。
- 不创建带 `v1`、`v2`、`new`、`final-final` 等迭代痕迹的项目文件名。
- 数据库结构只通过 Drizzle schema 和语义明确的迁移推进，不保留长期双实现。
- 保留用户已有的未提交改动；修改前先看 `git status --short`，不得覆盖无关工作。
- PostgreSQL 仍是唯一业务数据源；Redis 只负责队列和实时分发。
- 不恢复已退役的通用聊天工作台、通用会话 API 或 WebSocket。
- 不展示或保存模型的隐式思维链。前端与导出只展示公开依据：观察到的事实、引用、采用的规则、决策、置信度和下一步动作。

### 1.3 前端边界

- 保留现有视觉语言、三工作台结构和主要布局。
- 允许新增一个顶部“验证”页面。
- 现有页面只做能增强业务闭环的小改：增加来源、关联、解释、状态和跳转。
- 不做炫技式 Agent 动画，不用虚构进度，不把日志流包装成“智能”。
- 任何新增展示必须有真实后端数据或确定性计算支撑。

### 2.2 高分线

赛题高分的关键不是“功能更多”，而是以下能力有可复现证据：

1. **多 Agent 协同不是单模型串行换人设**：节点有不同输入权限、不同输出契约、明确依赖、独立失败处理和可观察分歧。
2. **幻觉治理不是模型自评**：事实声明必须绑定领域证据；反方能寻找反例和边界；裁决同时使用确定性规则与独立 Agent，且只能收紧不能放松。
3. **个性化不是改语气**：画像要改变学习目标拆分、先修补强、脚手架、难度、资源结构和下一步动作；专业事实与证据引用不能因画像而漂移。
4. **结果可被第三方复核**：给出运行清单、中间产物、引用关系、散列、规则版本、模型路由、裁决记录和离线验证脚本。
5. **指标不是自说自话**：不少于 50 个案例；至少 3 组画像；幻觉率、难度适配率、核心知识覆盖率的口径、分母、空值和离线回放核验方法都必须固定。
6. **具备迁移方法**：说明更换领域时哪些模块复用、哪些数据替换、需要哪些黄金集，而不是临时再写一套系统。

## 4. 核心创新方案：学情图—声明证据图—协同运行链

### 4.1 方法定义

本项目下一阶段的技术方法命名为：

**VACP：Verifiable Agent Collaboration Protocol，可验证智能体协同协议。**

VACP 不是新框架，而是建立在当前 StudyRun 上的一组工程契约：

- 每个执行者只能读取契约允许的输入引用。
- 每个节点必须输出结构化公开产物，而非只输出聊天文本。
- 每个产物记录生产者、输入引用、结果、公开理由、不确定性和内容散列。
- 每个下游节点通过产物 ID 引用上游，不复制一段无法定位来源的自由文本。
- 每次修订产生新产物，旧产物不可覆盖。
- 任意运行可在不调用模型的情况下回放：重建 DAG、核对散列、检查证据边、重算指标和发布规则。

### 4.2 双图一链

#### 学情图

节点是知识点，边是先修、分支、应用和复习关系；节点状态包含 BKT 掌握概率、置信度、作答和反馈来源。

它回答：

- 学习者当前会什么、不会什么？
- 哪个先修缺口影响当前任务？
- 为什么资源需要降阶、保持或进阶？
- 本轮学习后哪个状态发生了变化？

#### 声明证据图

节点包括事实 Claim、证据、反方议题和裁决；边包括支持、部分支持、冲突、边界限制和引用。

它回答：

- 资源中的事实来自哪里？
- 哪些 Claim 找不到证据？
- 哪些证据彼此冲突？
- 为什么某条内容被修改、删除或禁止发布？

#### 协同运行链

链由 StudyRun DAG、节点 attempt、Agent 产物、事件和发布决定组成，连接学情图和声明证据图。

它回答：

- 哪个 Agent 在什么输入下产出了什么？
- 哪个决定改变了后续节点或触发修订？
- 同一任务换一个学习者后，哪些决策发生变化？
- 不运行模型时，第三方能否验证最终资源的发布依据？

### 4.3 执行者与角色分离

保留当前六类业务角色，但增加更明确的 `actorKey`。角色用于权限和用户选择，执行者用于区分真实工作职责：

| actorKey | 归属角色 | 公开输入 | 公开产物 |
|---|---|---|---|
| `learner_modeler` | learning_planning | 目标知识点、BKT、路径、历史反馈 | learner_snapshot、design_constraints |
| `structured_retriever` | evidence_retrieval | 任务、数据集范围 | structured_evidence |
| `document_retriever` | evidence_retrieval | 任务、允许文档范围 | document_evidence |
| `domain_analyst` | domain_expert | 证据集合，不读取生成草稿 | domain_brief、professional_boundaries |
| `resource_author` | resource_generation | 学情约束、领域简报、证据 | resource_draft |
| `claim_auditor` | cross_validation | 草稿、证据 | atomic_claims、deterministic_checks |
| `red_team_critic` | cross_validation | 草稿、Claim、证据；不读取生成端理由 | challenge_set、counterevidence_requests |
| `evidence_judge` | cross_validation | Claim、证据边、质询、规则结果；不读取生成端对话 | adjudication |
| `privacy_guard` | privacy_compliance | 输入元数据、引用范围 | privacy_decision |
| `publisher` | cross_validation | 所有门禁结果 | publication_decision |

必须做到：

- `red_team_critic` 与 `resource_author` 不共享对话历史。
- `evidence_judge` 不读取生成端自我解释，只读取可公开材料。
- 即使三者使用同一个底层模型，也要有独立系统提示、独立输入包、独立产物记录；模型路由与参数写入 producer 元数据。
- 确定性规则裁决与 Agent 裁决并行保留，最终取更严格者。

### 4.4 标准 Agent 产物

新增统一产物契约，建议在 `server/runs/artifacts.ts` 定义：

```ts
interface CollaborationArtifact {
  id: string;
  runId: string;
  learnerId: string;
  nodeKey: RunNodeKey;
  actorKey: string;
  attempt: number;
  artifactType:
    | 'learner_snapshot'
    | 'design_constraints'
    | 'evidence_set'
    | 'domain_brief'
    | 'resource_draft'
    | 'claim_audit'
    | 'challenge_set'
    | 'adjudication'
    | 'privacy_decision'
    | 'publication_decision'
    | 'learning_decision';
  inputRefs: string[];
  payload: Record<string, unknown>;
  publicRationale: {
    observations: string[];
    basisRefs: string[];
    decision: string;
    uncertainty: string[];
    nextAction: string | null;
  };
  producer: {
    kind: 'agent' | 'rule' | 'tool' | 'mixed';
    model: string | null;
    promptHash: string | null;
    settingsHash: string | null;
  };
  contentHash: string;
  createdAt: number;
}
```

实现要求：

- 使用 Node `crypto` 的 SHA-256，不新增依赖。
- 对 JSON key 做稳定排序后散列，保证离线重算一致。
- `payload` 只保存公开结果，不保存隐式思维链。
- 临时上传正文不得进入 artifact，只保存文件名、字节数、散列、是否保留和审计结论。
- `study_runs.context_json` 可以继续作为执行缓存，但不得再作为唯一审计来源。

### 4.5 Claim 生命周期

每个事实 Claim 必须经历以下可追踪状态：

```text
drafted
  → extracted
  → evidence_linked
  → challenged
  → adjudicated
  → revised / released / manual_review
```

需要记录：

- 所属 `draftArtifactId` 与 `attempt`。
- Claim 类型：数值、字段含义、方法步骤、因果判断、风险建议、非事实教学表达。
- 证据边：`supports`、`partially_supports`、`conflicts`、`limits`。
- 确定性检查：数字是否精确出现、数据定位是否存在、字段是否在 schema、引用是否越出允许数据集。
- 批评议题和裁决。
- 若修订，记录 `supersedesClaimId` 或同一 logical claim 的前后映射。

发布规则必须 fail closed：

- 没有 Claim 审核产物，不发布。
- 存在 unsupported，不发布。
- 存在 conflict，不发布。
- 高风险任务存在 partial，不发布。
- 数值 Claim 未通过确定性核验，不发布。
- 证据引用越出允许范围，不发布。
- 修订预算用尽后自动拒绝发布、不入库，保留可回放记录供下一次智能体补充核验；不把资料审核责任交给普通学习者。

### 4.6 个性化—事实保真解耦

赛题背景的核心矛盾是：个性化越强，内容越可能失真；约束越强，资源越可能千篇一律。本项目应将两类属性分开验证：

- **允许随画像变化**：难度、脚手架、术语解释深度、示例顺序、先修补强、题目层级、下一步动作。
- **不允许随画像漂移**：字段含义、数据值、行业边界、证据定位、故障因果强度、来源许可。

为此增加反事实评测：同一任务分别输入 foundation、advanced、maintenance 三种画像。

输出两个辅助指标：

1. `personalizationSensitivity`：应该变化的教学属性中，实际发生合理变化的比例。
2. `factualConsistency`：三份资源的共享事实中，证据与结论保持一致的比例。

可再给出调和指标 `personalizedFidelity`，但它只作为创新辅助指标，不能替代赛题规定的三项核心指标。

### 4.7 动态编排升级

当前 planner 在运行前生成一次计划。升级后采用“两阶段策略决策”，仍保持现有 DAG 框架：

#### 运行前计划

从目标知识点及先修闭包提取真实信号：

```text
profileUncertainty = 1 - 目标知识点与先修点的加权平均 confidence
knowledgeRisk      = 0.5 × 近期错误率 + 0.3 × 先修缺口 + 0.2 × 掌握不确定性
taskRisk           = 资源类型风险 + 数值/因果/操作指令密度
```

不得继续只用“有没有学习历史”估算画像不确定度。

#### 检索后策略修正

结构化检索和文档检索完成后，由纯函数 `deriveVerificationPolicy` 根据实际证据产物修正审核策略：

- 证据为空或覆盖低：标记 `sparse`，禁止强事实表达，启动反证/边界检索。
- 数据与文档结论不一致：标记 `conflict`，裁决必须从严。
- 数值和因果 Claim 密度高：启用数值核验与越界因果规则。
- 学情置信度低：增加难度适配质询，不增加事实宽松度。
- 资源为知识图谱或复习卡：可减少生成型调用，但门禁不减少。

策略变化追加 `plan.amended` 事件并生成 policy artifact；不直接修改已完成节点。

#### 目标

#### 主要文件

#### 离线验证脚本

`verify-run-export` 必须检查：

- manifest 与 artifact hash 是否一致。
- DAG 依赖是否闭合、事件 seq 是否连续。
- 所有 inputRefs 是否存在。
- Claim—Evidence 是否有悬空引用。
- 每轮 adjudication 是否与规则结果一致或更严格。
- final asset 是否来自已 released 的 publication decision。
- 导出中是否含敏感字段或临时正文。

`replay-run` 必须做到：

- 不连接模型。
- 根据 artifact 和规则重算 Claim 汇总、门禁结果和指标。
- 输出“通过/失败 + 具体差异”，非零退出码表示校验失败。

#### 官方三项指标口径

1. **幻觉率**：`unsupported 事实 Claim / 全部可审计事实 Claim`。`non_factual` 不入分母，空分母必须报告 N/A，不能当作 0。
2. **难度适配准确率**：目标区间、脚手架规则、画像状态均匹配的案例数 / 全部案例数。预测适配与真实作答适配分开报告。
3. **核心知识覆盖率**：有有效 evidence edge 支持的必备知识点 / 黄金必备知识点。不能只凭资源文本包含关键词判定。

#### 补充指标

- 初稿幻觉率与终稿幻觉率。
- 门禁净增益：`draftHallucinationRate - finalHallucinationRate`。
- 有效质询率：被规则/人工确认有效的议题 / 全部议题。
- 修订成功率与平均修订轮数。
- 证据来源多样性与冲突率。
- personalizationSensitivity。
- factualConsistency。
- personalizedFidelity。
- 节点耗时、失败率、重试率和降级率。

#### 消融组

| 组别 | 配置 | 证明目标 |
|---|---|---|
| A | 单生成器 + 证据，无质询裁决 | 基线 |
| B | 多节点生成 + Claim 规则审核，无 red-team | 规则审核贡献 |
| C | 完整幻觉治理，但固定中性画像 | 个性化耦合贡献 |
| D | 完整 VACP | 最终系统 |

- 覆盖 AI4I、MetroPT-3、六类资源、基础/进阶/迁移。
- 12 个分层样本和所有失败案例执行离线回放与可追溯记录核验。
- 核验记录必须保留运行 ID、日期、Claim verdict、难度评价、覆盖缺口和修复建议。
- 报告区分：离线规则结果、存量真实运行结果、本次 live 结果、回放核验结果。
- 未完成 60 案例 live 时必须如实写“分层 live + 全量离线”，不能笼统称全量实测。

#### 验收

- 篡改导出内任一 artifact 能被 hash 校验发现。
- 删除 evidence edge 能被完整性校验发现。
- 修改 adjudication 为宽松结果能被 replay 发现。
- 三项官方指标口径固定且有单元测试。
- 消融报告不再以 final=0 就推断门禁有效，必须展示 draft 与 final 的对照。

### 里程碑 G：前端轻量增强与“验证”页面

#### 目标

不改变现有设计骨架，让普通用户和评委能看懂系统为何做出某个决定。

#### 新增页面

在 `web/src/app/page.tsx` 的顶层视图增加 `validation`，新增：

- `web/src/components/validation-workbench.tsx`
- 必要时增加小型 `run-trace-panel.tsx`，不要拆成大量组件。

#### 验证页结构

1. **运行选择区**：列出当前用户最近运行、任务、状态、最终资源和时间。
2. **可信摘要**：证据条数、事实 Claim 数、支持/部分/冲突/无证据、修订次数、发布结论。
3. **协同链**：沿现有 DAG 展示每个 actor 的输入引用、公开结论、耗时和产物 hash；默认折叠。
4. **声明证据表**：Claim、类型、证据定位、反方议题、裁决和所属轮次；优先使用清晰表格，不强行做复杂图形。
5. **前后对照**：初稿与终稿，或者同一用户两次 run；突出哪些教学内容变化、哪些事实保持不变。
6. **离线校验结果**：完整性、散列、引用、门禁规则是否通过。
7. **导出入口**：下载比赛证据包。

##### 路径页

## 7. 详细测试策略

### 7.1 单元测试

至少覆盖：

- artifact 稳定散列与引用。
- 学情信号计算。
- verification policy。
- Claim 分类与确定性核验。
- 判决严重度合并。
- feedback → learning decision。
- 三项官方指标。
- 反事实个性化指标。
- 导出脱敏规则。

不追求机械测试数量，但新增核心纯函数应至少一正一反一边界案例。建议在现有 115 个基线上增加约 30 个高价值用例。

### 7.2 服务集成测试

不增加测试框架，使用现有 Vitest、Node fetch 和本地 PostgreSQL/Redis：

- 创建 run 后 snapshot/artifact 是否落库。
- 重复 idempotency key 是否返回同一 run。
- 节点失败/重试是否只产生正确 attempt 产物。
- SSE 断线后事件 seq 能否回放。
- 取消后是否禁止后续发布。
- 跨 learner 访问 run、artifact、asset、decision 是否 404。
- Worker 重启后是否能从 DB 引用恢复。

模型调用使用桩响应，不能为自动测试调用外部 API。

### 7.3 幻觉故障注入测试

建立固定 fixture，不依赖 live 模型：

- 错数字。
- 错单位。
- 错字段。
- 错数据定位。
- 越界因果。
- 冲突证据。
- 无证据操作建议。
- 看似专业但不可核验的阈值。

每类错误必须记录由哪个规则或 actor 拦截，以及未拦截时为什么。

### 7.4 离线回放核验

离线回放核验不可以只看最终总分。每个样本至少回答：

- 是否存在事实错误？
- 证据是否真正支持该 Claim？
- 引用能否定位？
- 资源难度是否适合画像？
- 必备知识点是否真正讲到？
- 行业边界是否表达清楚？
- 下一步学习动作是否合理？

### 7.5 回归门禁

每个里程碑完成后至少执行：

```text
pnpm test
pnpm typecheck
```

前端改动完成后再执行已有前端构建；若构建工具试图联网或安装，立即停止并报告。

## 8. 指标目标与完成定义

### 8.1 比赛硬指标

- 幻觉率 `< 5%`。
- 学习者画像—资源难度适配准确率 `≥ 85%`。
- 核心知识覆盖率 `≥ 90%`。
- 不少于 50 个评测案例，本项目固定 60 个。
- 不少于 3 组差异化画像，本项目固定 foundation、advanced、maintenance。

### 8.2 工程指标

- 运行事件 seq 连续、无重复。
- artifact 引用完整率 100%。
- artifact hash 校验通过率 100%。
- 已发布资源全部有 publication decision 和 Claim audit。
- 跨 learner 隔离测试 100% 通过。
- 模型不可用时，规则门禁仍 fail closed。
- 自动测试不访问外网。

### 8.3 创新证明指标

- 完整系统的终稿幻觉率显著低于无门禁基线。
- critic 能发现规则审核未覆盖的有效问题；若没有发现，也必须如实报告而非伪造贡献。
- 三画像的教学属性存在合理差异。
- 三画像共享事实的 factualConsistency 保持高水平。
- 第三方离线 replay 与在线记录的发布结论一致。

### 8.4 最终 Definition of Done

只有同时满足以下条件，才可以标记本轮完成：

1. 每个 StudyRun 节点都有可验证 artifact。
2. 初稿、修订稿和终稿 Claim 可按轮次追踪。
3. run_start、generation_end 和反馈后状态可比较。
4. 作答/反馈能产生持久化 learning decision，并能发起下一 run。
5. 验证页能展示真实协同链和声明证据关系。
6. 离线验证与回放脚本通过。
7. 60 案例评测口径完整；live 与离线结果如实区分。
8. 三项赛题指标达标，或明确列出未达标项和修复计划。
9. 现有测试与新增测试全绿，类型检查通过。
10. 比赛要求的文档、三画像数据包和演示脚本齐备。
11. 全过程未在无授权情况下下载依赖、数据或模型。

## 9. 风险与控制

| 风险 | 表现 | 控制措施 |
|---|---|---|
| 过度架构化 | 为了协议新增大量抽象，影响截止时间 | artifact 只做一个统一表和少量纯函数；不引入框架 |
| 模型判断相关性 | author、critic、judge 同源 | 输入隔离、独立 promptHash、规则结果兜底、裁决只收紧 |
| 指标虚高 | 关键词覆盖、空 Claim 当 0 幻觉 | 黄金知识点—证据边、N/A 语义、离线回放核验 |
| 修订环无法证明 | 正常样本从不触发修订 | 使用固定故障注入 fixture，live 只在授权后做少量分层案例 |
| 前端信息过载 | 验证细节挤占学习体验 | 默认摘要、按需展开、独立验证页 |
| 截止前材料不足 | 只写代码不整理证据 | 里程碑 H 与开发同步，不留到最后一天 |
| 流量不足 | 下载依赖/数据、全量 live 调用 | 默认离线、禁止下载、live 开关默认关闭 |
| 历史数据兼容 | schema 修改导致已有演示数据失效 | 新字段兼容默认值、迁移前备份、禁止 destructive reset |
| 隐私泄露 | artifact/export 保存上传正文或密钥 | 白名单导出、敏感字段测试、临时资料只存元数据和 hash |

## 11. 交给开发 Agent 的执行规则

开发 Agent 每完成一个里程碑必须执行以下循环：

1. 重新阅读本里程碑目标与验收标准。
2. 检查工作区现有改动。
3. 只修改本里程碑涉及的文件。
4. 先写或更新纯函数测试，再接入数据库和 API。
5. 用现有依赖实现，不下载任何内容。
6. 运行测试与类型检查。
7. 在 `progress.md` 记录：改了什么、验证了什么、还缺什么、是否发生网络调用。
8. 在 `findings.md` 只记录仍然有效的架构决策，不堆积过程日志。
9. 验收通过后再进入下一里程碑。

遇到以下情况必须暂停并询问用户：

- 必须新增依赖才能继续。
- 必须下载新数据或重新生成大量嵌入。
- 必须进行大规模 live 模型评测。
- 必须大改现有三个前端工作台。
- 迁移需要删除或覆盖现有数据。
- 发现用户已有改动与计划修改发生实质冲突。

## 12. 最终对外叙事

最终答辩不应把项目描述成“十个节点、六个 Agent、很多技术名词”。应聚焦一个问题、一个方法、三类证据：

### 问题

单模型在垂直教育中无法同时保证个性化和专业真实性：越迎合学习者，越可能产生专业漂移；越严格限制，越容易变成千人一面的静态内容。

### 方法

学情图决定教学策略，声明证据图约束事实边界，协同运行链组织并记录 Agent 间的分析、生成、质询、裁决和反馈决策。每一步都产生可验证产物，最终结果可以离线回放。

### 证据

1. 三类背景学习者在同一任务上的路径、难度和脚手架确实不同。
2. 初稿—质询—修订—终稿的 Claim 数据证明幻觉治理产生实际增益。
3. 60 案例、三项硬指标、消融实验和离线验证证明方案有效且可借鉴。

这才是本项目下一阶段真正需要完成的“创新性”：不是再加一个 Agent，而是把多 Agent 协同从流程展示提升为可验证、可复用的工程方法。
